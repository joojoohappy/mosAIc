架構

一個請求走過的路

重點不是有幾個方塊，而是：三條路徑都先決定 mode，才匯流到唯一一次寫檔。因此超時後才回來的殭屍 thread 不可能覆寫已經寫好的 cached 結果。

誠實層

三種結果模式

mode 和 sourceNote 都由伺服器產生，前端原樣顯示。誠實不是前端的樣式選擇 — 把這句話留在伺服器，UI 才不可能不小心說謊。

live provider 成功，回傳的 bytes 通過圖片檢查，用了使用者這次的照片。

實作約束

三條不變量

違反任何一條，「伺服器不說謊」這個保證就破了。改 generate.py 之前先讀。

  1. _call_provider() 只回傳 bytes，絕不碰檔案系統。所有寫入都在 _write_result()，在 mode 決定之後發生一次。超時後才回來的殭屍 thread 因此不可能覆寫已經寫好的 cached 結果。
  2. mode: "live" 代表真的握有一張圖。provider 的輸出要過跟上傳同一套 _is_image()；回 200 但內容是文字（安全拒絕、把 prompt 當成問答）→ 視為失敗 → fallback。
  3. 使用者的照片不保留。bytes → provider → 丟掉，storage/ 底下沒有任何使用者輸入。誠實的但書：Starlette 會把大的 multipart 先 spool 到暫存檔，request 結束時刪除 — 我們沒有複製到任何地方，但「完全不落地」講得不精確。
約束為什麼
route 一律用 def，不用 async defStarlette 會丟進 threadpool。同步 SDK 卡 40 秒不會凍住 event loop。已實測
圖片判斷用 magic bytes，上傳與 provider 輸出共用同一個函式一個信任邊界，一份定義
寫入順序：先圖片，後 JSON；JSON 走 tmp + os.replace前端拿到 resultId 會立刻 GET，不能讀到半份 JSON 或指向不存在的圖
路徑用 Path(__file__).parent 解析，不相對 cwduvicorn 從 repo root 起、測試從 backend/ 起。兩種都實測過
API key 從 backend/.env 讀，不從 shell 環境變數generate.py 呼叫 load_dotenv()，所以 unset shell 變數不會關掉 live — 要註解掉 .env 裡那一行。範本在 backend/.env.example
resultId 進檔案路徑前必須通過 ^[0-9a-f]{32}$traversal 是 404，不是一次檔案讀取
timeout 由 pregen 實測值決定，零重試現場重試會讓最壞等待加倍。實作在 _call_provider 時一起寫
# run_generation 的骨架 —— 唯一決定 mode 的地方
img, mode, reason, meta = None, "mock", None, None

if API_KEY:
    try:
        img = _call_provider(recipe["prompt"], image_bytes)   # 只回 bytes
        if _is_image(img) is None:
            raise ValueError("provider returned bytes that are not an image")
        mode = "live"
    except Exception as err:
        img, reason = None, f"{type(err).__name__}: {err}"[:200]
else:
    reason = "no_api_key"

if img is None:
    img, mode, meta = _load_fallback(recipe["id"])      # cached | mock

return _write_result(recipe, img, mode, meta, reason)   # 唯一寫檔處
