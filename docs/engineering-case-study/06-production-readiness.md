# 06 · Production readiness

## Classification: **Validated Prototype**, approaching Production-Oriented

| Level                   | Meaning                                                                                                                                | MOSAIC                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Prototype               | Works on a developer machine                                                                                                           | passed                                                                       |
| **Validated Prototype** | Behaviour verified by automated tests and measurements, against stand-ins for external systems                                         | **here**                                                                     |
| Production-Oriented     | Built with production concerns (limits, failure handling, CI, config) _and_ exercised once on the real platform with real dependencies | design yes, **verification no**                                              |
| Production-Ready        | Verified on staging with real dependencies; monitoring, runbook, rollback tested                                                       | no                                                                           |
| Production-Deployed     | Serving real users with observed operations                                                                                            | no: production serves `main` (`c76a78a`) which cannot generate images at all |

**Why not Production-Oriented yet:** the design has most production concerns, but three things that decide whether it works in production have never run: a real Gemini call, a real Vercel Blob store, and a smoke test against a deployed preview. No recipe is open (`tryReady: false` on all three), so the public site cannot generate anything even after deploy. Passing local tests against a fake model is evidence about MOSAIC's code, not about the system.

## What would move it up a level

To **Production-Oriented** (a few hours of owner work, small cost):

1. Create the Gemini key with a provider-side spend cap; connect Blob; set the secrets.
2. Verify one recipe's rights and set `tryReady: true`.
3. Run `scripts/smoke.sh` and one `SMOKE_GENERATE=1` call against a preview; record latency and cost of that call.

To **Production-Ready**: 4. Structured logs with a request ID and a daily summary (calls, fallbacks by reason, spend). 5. An alert when the fallback rate or spend crosses a threshold. 6. A short runbook: rotate the key, roll back (Vercel Instant Rollback to a known build), turn live generation off (remove the key). 7. Retention clean-up job for expired results.
