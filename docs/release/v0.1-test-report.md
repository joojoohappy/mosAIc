## What the browser tests cover

All E2E tests run the real website (Next.js), the real backend (FastAPI) and a **fake** image model server that speaks the Gemini Interactions protocol. They prove the product logic and the provider code path, **not** that Google's real API accepts our requests.

| Scenario from the brief         | Covered by                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Happy path, refresh, favorites  | "discover → recipe → create → live result → refresh → favorites"                                             |
| Invalid file type               | "limits, oversized and invalid files…" (fake PNG), `test_api.sh` "text renamed .jpg", "broken jpeg"          |
| Oversized upload                | Same E2E (> 8 MB refused in browser), `test_oversized_upload_is_413`, `test_body_cap_rejects_before_parsing` |
| Large but allowed photo         | "a 4–8MB photo is shrunk in the browser to fit hosting limits"                                               |
| Missing recipe / missing result | "missing recipe and result show clear errors"                                                                |
| Recipe not cleared for Try      | "recipes not yet verified cannot be tried, even by direct URL"                                               |
| Provider error                  | "model errors and timeouts end in an honest fallback" (HTTP 500 from the model)                              |
| Provider timeout                | Same test (model hangs past `MOSAIC_PROVIDER_TIMEOUT`)                                                       |
| Rate limits / daily limits      | E2E messages for 429/503; `test_limits.py` for the limits themselves                                         |
| Forged visitor headers          | `test_spoofed_forwarded_for_does_not_reset_the_limit`, `tests/proxy.test.mjs`                                |
| Duplicate clicks                | "download, explore more, and a double click pays once"                                                       |
| Refresh during generation       | "refreshing during generation and trying again does not pay twice"                                           |
| No model key (demo mode)        | "demo mode is announced before uploading when no model key is set"                                           |
| Narrow mobile screens           | "every page fits a 390px phone screen without sideways scrolling"; axe at 390 px                             |

All E2E uploads pass through `apps/web/proxy.ts` with the visitor-IP signing turned on, as on Vercel.

## Accessibility, links, performance

`tests/e2e/quality.test.mjs` builds the site for production and checks 12 routes (home, two recipes, two create pages, a result, my recipes, about, privacy, terms, unknown recipe, unknown page).

- **Accessibility (axe-core 4.14, WCAG 2.0/2.1 A + AA + best practice), 1280 px and 390 px:** first run found serious issues: low-contrast grey text (2.3–2.5:1), blue section labels (3.7:1), links in text distinguished only by colour, a scrollable prompt box that keyboard users could not focus, and recipe cards whose accessible name did not match the visible text. All fixed; re-run has **0 serious or critical** violations. One "moderate" remains (no `<h1>` on the "recipe not found" state), logged for v0.2.
- **Internal links:** `/`, `/about`, `/create/seed-01`, `/my-recipes`, `/privacy`, `/recipe/seed-01`, `/recipe/seed-02`, `/recipe/seed-03`, `/terms` all answer 200. External links (two Threads posts, GitHub, Google's Gemini terms) are listed and all use HTTPS; they were not fetched because this sandbox cannot reach them.
- **Performance (local production build, Chromium, no throttling):** TTFB 5–22 ms, LCP 132–332 ms, 145–152 KB of JavaScript per page (compressed). Budget is LCP < 2.5 s and ≤ 400 KB JS. These are local numbers; they do not include network latency or a cold Vercel function.

## Deployment smoke test

`scripts/smoke.sh <url>` checks a deployed site read-only: home, privacy, terms, `/api/health`, recipe list and detail, 404s, that API docs are hidden, and that generate validates input. With `SMOKE_GENERATE=1` it also runs **one** real, billable generation and checks the result is `live`.

- Against a local stack: 10 / 10 read-only checks passed; the generate path was exercised.
- Against a simulated Vercel SSO redirect: exits with code 3 and "set VERCEL_BYPASS" (the GitHub workflow turns that into a skipped-with-notice run when the secret is not configured).
- Against the real Vercel previews (`https://mos-a-ic-nknmxl0bz-joojoohappy.vercel.app` web, `https://mos-a-ic-82n59hahz-joojoohappy.vercel.app` API, commit `205b3e0`): every request was redirected to Vercel's login (HTTP 302). **No staging smoke test has passed yet.** This sandbox cannot reach `*.vercel.app` directly.

## Not verified

- **A real Gemini call.** No key was available. The request and response shapes follow Google's published documentation for `gemini-nano-banana-2.1` and are tested against a fake server, but a real call may still reveal differences. If it does, the app falls back to an honest `cached`/`mock` result instead of failing.
- **Vercel Blob in production.** Tested against a fake Blob client with the SDK's real method names and arguments, not against a real Blob store.
- **Visitor IP on Vercel.** The signing proxy and the backend check are unit-tested; that Vercel's rewrite carries the signed header to the API project needs one check on staging (two devices should hit the per-visitor limit separately).
- **Lighthouse / screen reader** on the deployed site.
