# mosAIc v0.1 gap audit

Audited 2026-10-22 against `main` at `c76a78a` (the state before this release work), then re-checked against the release candidate on branch `claude/project-cleanup-readme` (PR #2).

Status values: **PASS** works and is verified · **PARTIAL** works with known gaps · **MISSING** not built · **BROKEN** built but does not work · **BLOCKED** needs something outside the repository · **UNKNOWN** cannot be checked from here.

## Summary

| Area                        | Before (`main`)                                 | Release candidate                                               |
| --------------------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| Core journey (4 pages)      | PARTIAL: pages built, no real generation        | PASS (E2E with a fake model server)                             |
| AI generation               | MISSING: `_call_provider` raised NotImplemented | PARTIAL: Gemini integration done, never run with a real key     |
| Recipes open for Try        | BLOCKED: all `tryReady: false`                  | BLOCKED: creators and usage basis still unverified              |
| Result storage on Vercel    | BROKEN: local disk, lost between requests       | PASS (Vercel Blob; live generation off without it)              |
| Cost and abuse controls     | MISSING                                         | PASS (configurable limits, budget, dedupe, concurrency)         |
| Upload security             | PARTIAL: magic bytes only                       | PASS (content decode, pixel cap, body cap)                      |
| Privacy and terms           | MISSING                                         | PARTIAL: pages written, need legal review                       |
| Tests, CI                   | PARTIAL: unit + shell API tests, no CI, no E2E  | PASS (unit, API, Playwright E2E, audits, CI)                    |
| Staging / production deploy | UNKNOWN: Vercel projects exist, not verified    | PARTIAL: previews build; smoke blocked by Deployment Protection |

## Findings

### F1. Discover → Recipe → Create → Result journey

- **Status:** before PARTIAL → now **PASS**
- **Evidence:** `tests/e2e/journey.test.mjs` "discover → recipe → create → live result → refresh → favorites" drives Chromium through all four pages against the real backend and a fake model server.
- **Missing work:** none for v0.1.
- **Risk / priority:** P0 (core product).
- **Verify:** `pnpm test:e2e`.

### F2. Live AI generation

- **Status:** before MISSING (`_call_provider` raised `NotImplementedError`; key variable was `ANTHROPIC_API_KEY`) → now **PARTIAL**
- **Evidence:** `apps/backend/app/provider.py` calls the Gemini Interactions API. `tests/test_generation.py` checks the request shape and response parsing; E2E runs the whole path against a fake server that speaks the same protocol.
- **Missing work:** one real call with a real key. The request format follows Google's published docs but has not been confirmed against the live service.
- **Risk / priority:** P0. If the real response shape differs, every generation falls back to `cached`/`mock` (no crash, no fake result).
- **Verify:** `cd apps/backend && .venv/bin/python -m scripts.pregen seed-01 photo.jpg` with `GEMINI_API_KEY` set, then `SMOKE_GENERATE=1 bash scripts/smoke.sh <staging-url>`.

### F3. Recipes open for Try

- **Status:** **BLOCKED**
- **Evidence:** `apps/backend/data/recipes.json` has `tryReady: false`, `creatorName: null`, `creatorInstagramUrl: null` for all three seeds. The API returns 403 `recipe_not_ready`.
- **Missing work:** confirm each creator, their Instagram link and the basis for running and showing their prompt; then set `tryReady: true`. This is a rights decision, so it is not made in code.
- **Risk / priority:** P0 for a useful public launch. Without it the public site can be browsed but nothing can be generated.
- **Verify:** `GET /api/recipes` shows `tryReady: true`; E2E "recipes not yet verified cannot be tried" keeps guarding the others.

### F4. API contract

- **Status:** before PARTIAL (docs drifted from code) → now **PASS**
- **Evidence:** `docs/architecture/api-contract.md` rewritten from the source, including how the original `GET /recipes`, `POST /generate` → `generation_id`/`status`/`result_image_url` sketch maps to `resultId`/`mode`/`imageUrl`. `tests/api.test.mjs` checks every documented error code.
- **Verify:** `pnpm test`.

### F5. Result storage and share links on Vercel

- **Status:** before BROKEN (results written to the function's disk, gone on the next request) → now **PASS** with a Blob store
- **Evidence:** `apps/backend/app/storage.py` (`BlobStore`), `tests/test_storage.py` end-to-end through a fake Blob client. Without a Blob store on Vercel, live generation is switched off (`live_blocker()` → `no_shared_storage`; test `test_vercel_without_blob_never_pays`).
- **Missing work:** connect a Blob store to `mos-a-ic-api` (owner action).
- **Risk / priority:** P0 for production.

### F6. Cost and abuse controls

- **Status:** before MISSING → now **PASS**
- **Evidence:** `apps/backend/app/limits.py`. Per-visitor rate (3/min) and daily (10/day) limits, a global daily budget of paid calls (50/day), a concurrency gate (2), duplicate detection (same recipe + photo within 10 min reuses the result). All configurable. Tests: `tests/test_limits.py` (`ApiLimits`), E2E "double click pays once", "refreshing during generation … does not pay twice".
- **Missing work:** set a hard spending cap in Google AI Studio (the in-app budget is not atomic across instances). Decide the real free-tier limits.
- **Risk / priority:** P0 (done) / P1 (provider cap, owner action).

### F7. Visitor identity for limits

- **Status:** found BROKEN in review (first `X-Forwarded-For` hop trusted, so anyone could reset their limit) → now **PASS**
- **Evidence:** `client_id` never reads `X-Forwarded-For`; `apps/web/proxy.ts` signs the platform IP with `MOSAIC_PROXY_SECRET`. Tests: `test_spoofed_forwarded_for_does_not_reset_the_limit`, `test_client_ip_from_website_needs_the_secret`, `tests/proxy.test.mjs`.
- **Missing work:** set the same `MOSAIC_PROXY_SECRET` on both Vercel projects. Until then every visitor on Vercel may share one bucket (stricter, not looser).
- **Risk / priority:** P0 (done) / P1 (env var, owner action).

### F8. Upload validation

- **Status:** before PARTIAL (magic bytes, 8 MB) → now **PASS**
- **Evidence:** `validate_upload` decodes with Pillow and caps pixels at 40 MP; `BodySizeLimit` refuses bodies over 8.5 MB before parsing; the browser shrinks 4–8 MB photos to fit Vercel's 4.5 MB limit. Tests in `test_limits.py` (`UploadValidation`), `tests/image-upload-wire.test.mjs`, E2E "a 4–8MB photo is shrunk".

### F9. Hidden prompts

- **Status:** **PASS**
- **Evidence:** `public_recipe` only adds `prompt` when `promptVisibility` is `public`; the web app has no copy of `recipes.json`; results and logs carry no prompt text. Test `test_hidden_or_unknown_visibility_never_leaks_the_prompt` in `test_generation.py`. All three current seeds are `public` (their prompts are already public posts).

### F10. Privacy, terms, retention

- **Status:** before MISSING → now **PARTIAL**
- **Evidence:** `/privacy` and `/terms` pages; consent line on Create; uploads are not stored; results expire after 30 days (`MOSAIC_RESULT_RETENTION_DAYS`); images served `private` through the API.
- **Missing work:** legal review of the two pages; automatic deletion of expired results from storage (now they are only no longer served).
- **Risk / priority:** P1.

### F11. Accessibility, mobile, broken links, performance

- **Status:** before UNKNOWN → now **PASS** for the automated checks
- **Evidence:** `tests/e2e/quality.test.mjs` runs axe-core on every page, follows every internal link, and records load timings against a production build. E2E checks a 390 px phone screen without sideways scrolling.
- **Missing work:** a manual screen-reader pass; Lighthouse against the real deployment.

### F12. Dependency vulnerabilities

- **Status:** before BROKEN (`next` and transitive `sharp`, `source-map-js` advisories) → now **PASS**
- **Evidence:** `pnpm audit` clean after Next 16.3.8 and overrides; `pip-audit` clean; Python direct dependencies pinned. Both run in CI.

### F13. CI

- **Status:** before MISSING → now **PASS**
- **Evidence:** `.github/workflows/ci.yml` runs `scripts/test-all.sh` plus audits on every push and PR; it passed on `205b3e0`.

### F14. Staging deployment and smoke test

- **Status:** **PARTIAL / BLOCKED**
- **Evidence:** Vercel builds a preview of both projects for every push to PR #2 (both "Deployment has completed" on `205b3e0`). `scripts/smoke.sh` and `.github/workflows/smoke.yml` test each preview, but previews are behind Vercel Deployment Protection, so the check could not reach them. The sandbox used for this work cannot reach `*.vercel.app` at all.
- **Missing work:** owner enables "Protection Bypass for Automation" and adds the `VERCEL_AUTOMATION_BYPASS_SECRET` repository secret, or runs `bash scripts/smoke.sh <preview-url>` from a logged-in machine; sets env vars on both projects.
- **Risk / priority:** P0 before calling anything "deployed and verified".

### F15. Demo video and README

- **Status:** before PARTIAL → now **PARTIAL**
- **Evidence:** public README (English + 繁體中文) with a recorded walkthrough GIF; demo video placeholder.
- **Missing work:** record the demo once live generation works on a verified recipe.

### F16. Licensing and third-party rights

- **Status:** **BLOCKED** (owner decision)
- **Evidence:** no license file; recipes are third-party prompts with unverified creators. No license has been added or assumed.
- **Missing work:** owner decides the project license and confirms the basis for each recipe.

### F17. Out-of-scope items

Login, creator submission, moderation, social features, payments, recommendations, bring-your-own provider and native apps are **not** part of v0.1 and were not built. `apps/mobile` remains a placeholder.
